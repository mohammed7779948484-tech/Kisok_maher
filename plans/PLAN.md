# Dragon Store Kiosk — Simplified Release Plan (v5)

> Updated: 2026-07-21  
> Target: a single store tablet, used by one customer at a time  
> Package manager: pnpm  
> Goal: ship the smallest safe, usable ordering flow quickly

**Implementation status:** Phases 0–3 are complete. Phase 4 automated gates and
HTTP/database smoke checks passed on 2026-07-21; the final hands-on tablet ordering
smoke remains an operator check once catalog items are added to the fresh database.

## 1. Product Model

The store owner hands one authenticated tablet to a customer. The customer browses,
adds items, confirms the order, sees the order number, and returns the tablet. The same
tablet and authenticated device session are then reused for the next customer.

This release deliberately does not introduce customer accounts, delivery details,
payments, customer names/phones, multiple concurrent kiosks, or distributed locks.

## 2. Final Simplified Decisions

### 2.1 Cart lifecycle

- Keep exactly one reusable cart row per authenticated device session.
- `expires_at` means cart-content inactivity expiry, not row deletion.
- Use a 20-minute inactivity window. Every add/update/remove action extends it.
- On the next access after expiry, clear stale items and reuse the same cart row.
- A successful order clears the cart inside the same database transaction and refreshes
  its expiry for the next customer.
- Do not add `active`/`processing` cart statuses.
- Add only:
  - `processing_key: string | null`
  - `processing_started_at: date | null`
- A cart is available when `processing_key` is null.
- A claim sets `processing_key` to the order idempotency key using a guarded bulk update.
- The same key represents the same retry. A different recent key means another submit is
  in flight. A claim older than two minutes is stale and may be recovered safely.
- Do not hard-delete cart rows in the customer request path. Long-term empty-row cleanup
  is deferred.

### 2.2 Duplicate-submit protection

- The client creates one UUID idempotency key for the current cart checkout attempt and
  retains it across a retry/refresh until the attempt succeeds or the cart changes.
- `orders.idempotency_key` is unique and indexed.
- Before work, during a claim conflict, and after a rollback, look up the key and return
  the already-created order when present.
- Stock decrement, order creation, item snapshots, cart clearing, and claim release all
  share one Payload transaction and the same `req`.

### 2.3 Confirmation privacy

- Generate a separate 32-byte random `confirmation_token`; never use the order number as
  the confirmation URL secret and never log the token.
- Store its expiry (24 hours) and open `/order-confirmation/[token]`.
- The token page contains no customer data and no prices.
- Pass the order number to a small client component but visually reveal it only after the
  customer taps the reveal button. This is a UX privacy curtain, not an authorization
  boundary.

### 2.4 Optional internal pricing

- Products themselves have no price. A product variant may have an internal numeric price,
  including zero, or no price.
- Public catalog, cart, metadata, order tracking, and confirmation DTOs/UI never include a
  price field.
- Payload field-level read access hides variant price from unauthenticated REST requests.
- Server order creation reads the authoritative price with Payload Local API and
  `overrideAccess: true`; it never trusts a browser-provided price.
- New orders store only `order_items.unit_price: number | null` as the useful snapshot.
- Existing `cart_items.price_at_add`, `order_items.total_price`, and
  `orders.total_amount` columns remain optional and hidden in Admin for compatibility,
  but the new flow does not write or read them.
- Admin totals, if needed later, are derived from `unit_price * quantity`; they are not a
  release blocker.

### 2.5 Database safety

- This release performs additive/relaxing schema changes only.
- Keep every existing database field in Payload configuration so development push cannot
  interpret this release as permission to drop a column.
- Do not run schema reset, `DROP SCHEMA`, broad migration cleanup, or live-data deletion.
- Apply and test schema changes on the confirmed development database (preferably a Neon
  branch) before pointing the app at store data.
- Generated Payload type/schema files are generated by Payload tooling and are never edited
  manually.

### 2.6 Deployment topology

- Supported release topology: one long-lived application process serving the one tablet.
- The existing bounded in-memory order-tracking limiter is sufficient for this topology.
- Shared/distributed rate limiting becomes required only if the app is later deployed with
  multiple instances or exposed as a broadly public service.

## 3. Implementation Phases

### Phase 0 — pnpm baseline

1. Add `packageManager` and pnpm configuration.
2. Produce a valid `pnpm-lock.yaml`; remove `package-lock.json` only after a frozen pnpm
   install succeeds.
3. Make existing scripts runnable with pnpm. Do not spend release time building a large
   new test harness.

Completion: `pnpm install --frozen-lockfile` works, or an external registry failure is
reported explicitly without pretending verification passed.

### Phase 1 — compatible Payload schema

1. Make variant price optional, internal, and hidden from unauthenticated field reads.
2. Add optional cart processing fields.
3. Add optional unique/indexed order idempotency and confirmation fields plus cart relation.
4. Relax and hide legacy customer/aggregate-price fields without deleting them.
5. Correct Admin field grouping with Payload `collapsible` layout fields.

Completion: schema diff is additive/relaxing only; no field/collection drop.

### Phase 2 — reusable cart and atomic order backend

1. Recover an expired session cart in place and clear only its stale contents.
2. Extend the 20-minute expiry on cart activity.
3. Remove browser price inputs and `price_at_add` writes.
4. Add a server-only order snapshot query that returns variant name, activity, stock, and
   nullable internal price.
5. Implement `placeOrderAction` with validation, cart claim, idempotency checks, one Payload
   transaction, atomic stock decrement, order/item creation, cart clearing, and claim reset.
6. Fix the existing variant-name mismatch (`variant.name` -> `variant_name`).
7. Keep cancellation stock restoration atomic if cancellation remains reachable.

Completion: one submit creates one order and decrements stock once; retry returns the same
order; failure leaves stock and cart unchanged.

### Phase 3 — kiosk UI and privacy cutover

1. Remove prices from public catalog/product/cart/tracking DTOs, props, metadata, and UI.
2. Replace the customer-details checkout form with a direct cart confirmation button.
3. Redirect `/checkout` to `/cart` so the old form is unreachable.
4. Add the token confirmation page and tap-to-reveal order number.
5. Keep order tracking by order number, with status/items only and no price/customer data.
6. Ensure Server Actions and Route Handlers independently validate the authenticated device
   session; middleware alone is never the authorization boundary.

Completion: a customer can browse -> add -> review -> confirm -> reveal the order number,
then the same tablet starts with an empty cart for the next customer.

### Phase 4 — focused verification and handoff

Run only the checks with the highest release value:

1. TypeScript strict typecheck and lint.
2. Focused unit/service checks for:
   - public DTOs contain no price keys;
   - nullable and zero internal prices are preserved correctly;
   - expired cart recovery reuses the same row;
   - idempotent duplicate submit does not duplicate order/stock decrement;
   - forced transactional failure preserves cart and stock.
3. One browser smoke path on the development database:
   browse -> add -> cart -> confirm -> reveal number -> cart empty.
4. Static search proving public UI/DTO code has no price formatting or checkout customer form.

Do not add exhaustive visual, concurrency, multi-instance, wire-protocol/RSC payload, or
full regression suites in this fast release. Do not inspect brittle RSC transport payloads;
verify typed DTOs, REST output, and visible DOM behavior instead.

## 5. Explicitly Deferred

- Physical deletion of legacy price/customer columns.
- Customer accounts, customer PII, delivery, payment, invoices, and online checkout.
- Multiple simultaneous kiosks or multiple application instances.
- Distributed locks/rate limiter/queues.
- Scheduled cart-row deletion.
- Broad test-suite creation or testing framework redesign.
- Persisted/aggregate order totals and price display to customers.

## 6. Release Acceptance Criteria

- One reusable cart per authenticated tablet session; contents expire after 20 minutes.
- A new customer never sees the previous successful customer's cart.
- Double-click/retry creates at most one order and decrements stock once.
- Transaction failure preserves cart items and stock.
- Missing and zero internal prices both work; neither is exposed publicly.
- No customer name, phone, address, notes, or honeypot form is required for ordering.
- Confirmation uses a separate expiring random token and reveals the order number on tap.
- Old database columns remain compatible and no destructive database operation is performed.
- pnpm is the documented package manager.
- Focused checks and the single-tablet happy-path smoke pass before store use.

## 7. Execution Commands

```powershell
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Run only focused test file paths while iterating. Run the final build only against validated
environment variables and a confirmed non-production database because Payload development
push is enabled outside production.
